# /user-test

PRD のターゲットユーザーからペルソナを生成し、Chrome連携でブラウザを実際に操作してユーザビリティのフィードバックを収集する。
ペルソナは1人ずつテストし、次に進むかはユーザーが判断する。

## 前提条件

- Claude Code が Chrome 連携済みであること（`--chrome` または `/chrome`）
- テスト対象のアプリが起動中でURLにアクセス可能であること

前提条件が満たされていない場合はユーザーに案内して中断する。

## Input（すべて読み込む）

- `docs/reqs/prd.md` — ターゲットユーザー、ペイン、提供価値
- `docs/reqs/product-model.json` — entities, actors, screens, transitions
- `docs/reqs/user-stories.md` — ストーリーとシナリオ
- `docs/specs/ui-spec.md` — 画面定義・インタラクション（存在すれば）

## Output

テスト結果をユーザーに提示する（ファイル出力はしない）。

## Execution Steps

### Step 1: 企画書を読み込む

prd.md と product-model.json は必須。存在しないかテンプレート状態の場合は中断する。
ユーザーにテスト対象のURLを確認する。

### Step 2: ペルソナを生成する

prd.md の「Who — User」セクションからテスト用ペルソナを生成する。
ペルソナの定義項目は prd.md の内容に応じて決める。以下は基本項目:

| 項目 | 内容 |
|---|---|
| 名前 | 架空の日本語名 |
| 年齢・職業 | prd.md のターゲットUser像に基づく |
| ITリテラシー | 低 / 中 / 高 |
| 利用シーン | prd.md の主な利用シーンから具体化 |
| 抱えている課題 | prd.md のUserのペインから具体化 |
| 性格・行動傾向 | 慎重派 / せっかち / 探索好き など |
| このプロダクトへの期待 | 提供価値に対する具体的な期待 |
| エクストリーム属性 | 該当する場合のみ。極端な特性とその背景 |

prd.md に競合製品、日常ツール、ドメイン固有の属性等の記載があれば、追加項目としてペルソナに反映する。

**生成ルール:**
- prd.md のロールごとに最低1人生成する
- ITリテラシーと性格のバリエーションを持たせる（全員同じにしない）
- actors に一般ユーザーと管理者がいる場合、両方のペルソナを生成する
- **エクストリームユーザーを必ず含める。** 以下の軸から prd.md の文脈に合うものを選ぶ:
  - **利用頻度**: ヘビーユーザー / 超低頻度
  - **スキル**: テクノロジーに非常に強い / デジタル機器にほぼ触れない
  - **身体的制約**: 視覚・聴覚・運動機能に制約がある
  - **環境**: 通信が不安定 / 非常に古い端末 / 移動中
  - **動機**: 機能を限界まで使い倒したい / 仕方なく使っている
  - **データ量**: 大量のデータを扱う / データがほぼ空の初回ユーザー

ペルソナ一覧をユーザーに提示し、調整の指示があれば反映する。
テスト順序もこのタイミングでユーザーに確認する。

### Step 3: テストシナリオを組み立てる

user-stories.md のシナリオ（Given/When/Then）をベースに、ペルソナが実際に体験する操作手順を構成する。

各シナリオについて:
1. **対象ストーリー**: US-ID を紐付ける
2. **操作の流れ**: screens の transitions に沿った具体的な操作手順（URLからの遷移を含む）
3. **注目ポイント**: 特に検証したい観点（初見での発見しやすさ、操作の手数、エラー時の挙動等）

### Step 4: ペルソナ1人ずつテストする

**1人ずつ順番に** テストする。各ペルソナのテスト完了後、ユーザーに次のペルソナに進むか確認する。

各ペルソナについて:
1. このペルソナの人物像をユーザーに提示する
2. テストシナリオの操作手順に沿って Chrome でブラウザを操作する:
   - 対象URLに遷移する
   - シナリオの各ステップを実際に操作する（クリック、入力、遷移）
   - 各画面でペルソナの視点から以下を評価する:
     - **第一印象**: 画面を見た瞬間、このペルソナは何に目がいくか
     - **迷いポイント**: 次に何をすべきかわかるか。ラベルやボタンの意味が伝わるか
     - **操作の手数**: 目的達成までのステップ数は適切か
     - **エラー体験**: バリデーションエラーやエッジケースの挙動
   - コンソールログにエラーがあれば記録する
3. このペルソナのフィードバックをまとめてユーザーに提示する
4. **ユーザーに確認する**: 「次のペルソナ（{名前}）に進みますか？ テストを終了しますか？」

ユーザーが終了を選択したら Step 5 へ進む。

### Step 5: フィードバックを統合する

テスト済みの全ペルソナのフィードバックを統合し、以下の形式で整理する。

```markdown
## ユーザーテスト結果

**実施日:** {日付}
**対象PG:** {PG名}
**テスト対象:** {テストしたストーリー/画面の範囲}
**テスト済みペルソナ:** {N}人 / 全{M}人

### ペルソナ別フィードバック

#### {ペルソナ名}（{ロール}・ITリテラシー{高/中/低}）

| 観点 | 評価 | コメント |
|---|---|---|
| 第一印象 | 😊/😐/😟 | {コメント} |
| 操作のわかりやすさ | 😊/😐/😟 | {コメント} |
| 目的達成のしやすさ | 😊/😐/😟 | {コメント} |
| つまずいたポイント | — | {具体的な箇所と理由} |
| 改善提案 | — | {ペルソナ視点での提案} |

### 共通の発見

- **強み:** {複数ペルソナに共通するポジティブな点}
- **課題:** {複数ペルソナに共通する問題点}

### 技術的な発見

- **コンソールエラー:** {検出されたエラーとその画面}
- **パフォーマンス:** {操作中に感じた遅延やレスポンスの問題}
- **レスポンシブ:** {レイアウト崩れ等の問題}

### 改善提案（優先度順）

| 優先度 | 対象 | 提案 | 根拠 |
|---|---|---|---|
| 高 | {画面/機能} | {提案内容} | {どのペルソナがどう困ったか} |
```

## 注意

- ペルソナは prd.md の定義から逸脱しない。架空の属性を過度に追加しない
- product-model.json にない画面・機能についてはテストしない
- フィードバックは「ペルソナとしての感想」であり、実装指示ではない。改善の判断はユーザーに委ねる
- データの書き込み（登録・削除等）を伴う操作がある。テスト用データで実施すること
- ログインが必要な場合、CAPTCHA等はユーザーに手動対応を依頼する
